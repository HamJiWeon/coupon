## HikariCP 커넥션 풀 튜닝

### 목적

커넥션 풀 크기(`maximum-pool-size`)가 TPS와 응답시간에 어떤 영향을 미치는지 확인한다.<br>
단순히 "크게 잡으면 좋다"가 아니라, 적정 크기가 어디인지 실측으로 확인하는 것이 목표다.

### 테스트 조건

- 테스트 유저 5,000명, 쿠폰 재고 5,000개로 초기화 (`TestInitializer`)
- k6 옵션: `vus: 30`, `duration: '20s'`
- 비교 지표: 전체 `iterations/s`가 아니라 **성공(200) 요청만의 응답시간(`{ expected_response:true }` 그룹)**

```js
export const options = {
    vus: 30,
    duration: '20s',
};

export default function () {
    const userId = Math.floor(Math.random() * 5000) + 1;
    http.post(`http://localhost:8080/coupons/1/issue?userId=${userId}`);
}
```

### 왜 `iterations/s`가 아니라 성공 요청의 응답시간을 기준으로 삼았는가

유저 수와 쿠폰 재고를 동일하게(5,000/5,000) 맞췄기 때문에, 한 유저는 딱 한 번만 성공(200)할 수 있고 나머지는 전부 중복 발급(409)으로 거절된다. 20초 동안 요청은 30만 건 넘게 나가지만 성공 가능한 요청은 최대 5,000건으로 고정되어 있어서, `http_req_failed` 비율(약 98%)이나 전체 `iterations/s`는 항상 비슷하게 나오고 커넥션 풀 크기와는 무관하다.

반면 **성공한 요청들의 응답시간**은 커넥션 풀 크기에 직접 영향을 받는다. 풀이 작으면 빈 커넥션을 기다리는 시간이 응답시간에 그대로 더해지기 때문이다. 그래서 이 값을 비교 기준으로 삼았다.

### 결과

| `maximum-pool-size` | 성공 요청 avg | 성공 요청 p(95) |
|---|---|---|
| 5 | 4.21ms | 13.14ms |
| 20 | 1.79ms | 4.86ms |
| 30 | 1.62ms | 5.08ms |

- 성공 건수는 세 경우 모두 정확히 5,000건으로 동일했다 (재고 초과 발급 없음 — 낙관적 락 + unique 제약이 고부하 상황에서도 정상 동작함을 재확인).

### 분석

**5 → 20**: p(95)가 13.14ms → 4.86ms로 약 63% 감소했다. VU(30명)에 비해 풀이 5개뿐이라 다수의 요청이 빈 커넥션을 기다리며 대기했고, 그 대기시간이 응답시간을 크게 늘렸던 것으로 보인다.

**20 → 30**: p(95)가 4.86ms → 5.08ms로 오히려 정체(사실상 오차 범위)했다. VU 수(30)와 풀 크기(20)가 이미 비슷한 수준이라 대기가 거의 발생하지 않는 상태였고, 그 이상 풀을 늘려도 병목이 다른 곳(H2 자체 처리 속도, 애플리케이션 스레드 등)으로 옮겨갈 뿐 커넥션 대기시간 감소로 이어지지 않았다.

> 커넥션 풀은 클수록 좋은 게 아니라, 동시 처리해야 하는 요청 수(VU)에 맞는 적정 크기가 존재한다. HikariCP 공식 문서에서도 `((core_count * 2) + effective_spindle_count)` 정도의 작은 값을 권장하는 이유가 여기에 있다.

### 결론

- 커넥션 풀이 너무 작으면(5) 명확한 병목이 된다.
- 동시 사용자 수와 비슷한 수준(20~30)이면 충분하고, 그 이상 늘리는 것은 이 조건에서는 효과가 없었다.
- "풀 크기 = 무조건 클수록 좋다"가 아니라 트래픽 패턴에 맞는 적정선이 있다는 것을 실측으로 확인했다.
