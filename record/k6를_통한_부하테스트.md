## 부하테스트 도구 선정

서버 성능 테스트 도구는 대표적으로 `k6`와 `JMeter`가 있다.<br>

## 성능 테스트의 이유
성능 테스트란 **시스템의 응답 시간**, **처리 속도**, **리소스 사용량(CPU, 메모리, 네트워크 등)** 을 측정하여 성능을 평가하는 테스트이다.

많은 개발자들이 목표하는 애플리케이션은 **"많은 사람이 사용해도 API 응답이 빠르고 안정적인 것"** 이다.<br>
하지만 이런 목표는 측정되지 않는 모호한 기준이다. 이러한 기준을 명확하게 할 수 있는 개념들을 알아보자.

### 처리량(Throughput)
시스템이 일정 시간동안 처리할 수 있는 작업(트랜잭션)의 개수를 의미한다.<br>
단위: TPS(Transaction per second), RPS(Requests per Second) 등으로 표현<br>
- ex) 초당 1,000개의 요청을 처리할 수 있다. = 1,000 RPS
  - 높을수록 좋은 지표이고, 시스템의 동시 처리 능력을 평가하는데 사용된다.

### 지연시간(Latency)
클라이언트가 요청을 보내고 응답을 받을 때까지 걸리는 시간<br>
단위: ms(밀리초), s(초)<br>
- 네트워크 지연, 서버의 처리 속도, 데이터베이스 응답 속도 등이 영향을 미친다.
  - 낮을수록 좋은 지표이고, UX(User Experience)에 큰 영향을 미친다.

성능 테스트를 진행하면서 유저 수가 늘어나면 처리량이 늘어나게 되고 어느 시점이 되면 유저 수가 늘어나더라도 처리량이 늘지 않고 유지되거나 떨어지는 경우가 발생한다.<br>
이런 시점이 어딘지 찾는 것이 **성능 테스트**이다.

## 부하테스트(Load Test)
목적: 예상되는 정상적인 부하(트래픽, 요청 수)에서 시스템이 안정적으로 동작하는지 확인한다.<br>
**특징**
- 시스템이 정상적으로 감당할 수 있는 최대 부하를 테스트
- 일반적인 동시 접속자 수, 요청 처리량 등을 기준으로 평가
- 예시로는 하루 평균 10만명이 접속하는 웹 사이트에서 동시 1,000명 접속시 정상 동작하는지 확인

## 스트레스 테스트(Stress Test)
목적: 시스템이 한계를 초과하는 부하에서 어떻게 동작하는지 확인하고, 장애 발생 시 복구 능력을 평가한다.<br>
**특징**
- 시스템이 감당할 수 있는 부하보다 더 높은 부하를 주어 언제, 어떻게 장애가 발생하는지 확인 장애 발생 후 시스템이 자동으로 복구되는지(회복력, Resilience) 평가
- 예시로는 1000명이 정상적으로 접속할 수 있는 서비스에 5,000명이 몰릴 경우 서버가 어떻게 반응하는지 확인

|구분|부하 테스트(Load Test)|스트레스 테스트(Stress Test)|
|---|---|---|
|목적|예상 부하에서 정상 동작 확인|최대 부하를 초과할 때 시스템의 한계 확인|
|테스트 강도|정상적인 범위 내 부하|비정상적인 초과 부하|
|목표|성능 저하 없이 일정한 처리 가능 여부|장애 발생 여부 및 복구 능력 확인|
|결과|시스템이 감당할 수 있는 최대 트래픽 파악|장애 발생 시 시스템 반응과 복구 과정 분석|

위의 두 테스트를 많이 진행하고 추가적으로는 아래의 테스트들도 존재한다.
- 스파이크 테스트(Spike Test)
  - 짧은 시간 동안 갑자기 많은 트래픽이 몰릴 때 시스템이 어떻게 반응하는지 테스트(선착순 쿠폰 오픈 시 트래픽 폭증)
- 지속 부하 테스트(Soak Test)
  - 장시간 높은 부하를 유지할 때 시스템의 안정성을 테스트(24시간 동안 높은 트래픽 유지)

그래서 이번에 부하테스트에서 **설치가 쉽고**, **JS를 사용해서 git으로 버전 관리가 가능하고**, **결과가 TPS(iterations/s) 중심**인 k6를 사용했다.

### 1차 baseline 테스트

```
export const options = {
  vus: 30,
  duration: '20s',
};

export default function () {
  const userId = Math.floor(Math.random() * 50) + 1;
  http.post(`http://localhost:8080/coupons/1/issue?userId=${userId}`);
}
```

**결과**
- `iterations`: 202,318건
- `iterations/s`: 10,114.74
- `http_req_failed`: 99.97%

### 발견한 문제
1. **유저 수 부족**: 테스트 유저가 50명뿐인데 20만 건 넘게 요청을 보냄 → `(user_id, coupon_id)` unique 제약으로 대부분 중복 발급(409) 처리됨. 실제 성공 가능한 요청은 최대 50건뿐이라 결과가 오염되었다.
2. **k6 기본 동작 이해 부족**: `sleep()`이 없으면 각 VU가 쉬지 않고 반복 요청함. VU 30개 × 20초 동안 응답시간(~3ms) 기준 이론상 약 20만 건이 나오는 게 정상 동작이었다.

→ `iterations/s`(10,114/s)는 "얼마나 빨리 요청을 처리(성공/거절 무관)했는가"를 보여준 것이지, "실제 발급 처리량"을 보여준 게 아니었다. 유효한 baseline이 아니라고 판단했다.

### 개선 방향
- 테스트 유저 수를 5,000명으로 확대 (`TestInitializer`)
- 쿠폰 재고도 5,000으로 맞춰서 대부분의 요청이 실제 성공하도록 조정
- k6 스크립트의 `userId` 랜덤 범위를 `1~5000`으로 확대
- 재측정 후 `http_req_failed` 비율이 정상 범위(대부분 성공)로 나오는지 확인 → 이 결과를 진짜 baseline으로 채택
