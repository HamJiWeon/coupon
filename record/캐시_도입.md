## 캐시 도입하기

이번 목표는 `GET /coupons/{id}`조회 API에 Redis 캐시를 붙여서 응답 속도를 개선하는 것이다.

우선 메인 클래스에 `@EnableCaching` 애노테이션을 적는다.

### `@EnableCaching`이 필요한 이유
- `@Cacheable`, `@CacheEvict`와 같은 애노테이션은 그냥 붙인다고 해서 자동으로 동작하지 않는다. 이 애노테이션들을 실제로 해석하고 캐시 로직을 끼워 넣는 **AOP 기능**이 기본적으로 꺼져있기 때문이다.

[동작 원리]
- Spring의 캐시 애노테이션들은 프록시기반으로 동작한다.
- `@Cacheable`이 붙은 메서드를 호출하면, 실제로는 Spring이 만들 프록시 객체가 먼저 요청을 가로채서 "이 메서드에 캐시 값이 있나?" 확인한다.
  - 확인했을 때 있다면 원래 메서드는 호출을 하지 않고 캐시된 값을 바로 반환한다.
  - 없다면 원래 메서드를 실행하고 결과를 캐시에 저장한다.

`@EnableCaching`을 붙이지 않는다고 해서 에러가 나지는 않는다. 그냥 `@Cacheable`이 조용히 무시되고, 매번 메서드가 그대로 실행된다. 겉으로 봐서는 뭐가 문제인지 알기 어렵지만 "왜 안빨라지지?"라는 생각이 든다면 `@EnableCaching`을 빼먹은 것이다.

### 그래서 "캐시" 라는게 무엇일까?
**Cache**는 자주 쓰는 데이터를 더 빠른 곳에서 미리 복사해두고, 다음에 필요할 때 원본대신 그 복사본을 쓰는 것이다.

**왜 필요할까?**
> 클라이언트 요청 → 애플리케이션 → DB(H2)에 쿼리 → 결과 받아서 → 응답

`GET /coupons/1`을 호출 할 때마다 매번 위와 같은 일이 일어난다.

근데 `couponId = 1`이라는 데이터는 안 바뀌고 `issuedQuantity`만 바뀌는데 조회는 계속 반복해서 들어온다.

매번 같은 DB까지 가서 똑같은 데이터를 다시 읽어오는 코스트는 낭비이다. 하지만 Cache를 쓰게 되면 이렇게 바뀐다.

> 1번째 요청: 클라이언트 → 애플리케이션 → DB 조회 → 결과를 Redis에도 저장 → 응답
> 2번째 요청부터: 클라이언트 → 애플리케이션 → Redis에서 바로 꺼내서 응답 (DB 안 감)

그래서 RAM에 데이터를 두는 Redis는 디스크 기반인 DB보다 훨씬 빨리 읽을 수 있다. 그래서 Redis에서 끝내면 응답속도가 빨라지고, DB부하도 줄어든다.

하지만 Cache는 복사본이기 때문에, DB가 바뀐다고 해서 Cache까지 같이 바뀌진 않는다. 그래서 쿠폰이 발급될 때마다 `@CacheEvict`로 Cache를 강제로 지워줘야 한다.

[캐시를 쓸 때 따라오는 트레이트오프]
속도를 얻지만, 최신 데이터가 항상 보장되지 않는다는 리스크를 관리해야 한다.

### 본격적으로 캐시 도입하기

**1. `TpsCouponApplication.java`에 `@EnableCaching`를 넣는다.**

**2. `RedisCacheConfig.java`를 만든다.**

```java
@Configuration
public class RedisCacheConfig {

    @Bean
    public RedisCacheManager redisCacheManager(RedisConnectionFactory redisConnectionFactory) {
        RedisCacheConfiguration configuration = RedisCacheConfiguration.defaultCacheConfig()
                .serializeValuesWith(
                        RedisSerializationContext.SerializationPair.fromSerializer(
                                new GenericJackson2JsonRedisSerializer()
                        )
                );

        return RedisCacheManager.builder(redisConnectionFactory)
                .cacheDefaults(configuration)
                .build();
    }
}
```
1. Bean으로 등록하기 위해 `@Configuration`을 쓴다.
2. 캐시 추상화(`@Cacheable`, `@CacheEvict`)가 실제로 Redis와 통신할 때 쓰는 `RedisCacheManager` 객체를 사용한다.
3. `RedisConnectionFactory`는 Redis 서버(localhost:6379)에 접속하는 방법을 담고 있는 객체인데, `application.properties`의 `spring.data.redis.host/port` 설정을 보고 Spring Boot가 자동으로 만들어서 `redisConnectionFactory`에 주입한다.
4. **function**
    - `defaultCacheConfig()`: Spring이 기본으로 제공하는 캐시 설정(만료 시간 X, key는 문자열로 직렬화 등)을 가져온다.
    - `.serializeValuesWith()`: 기본 설정 중에서 `value`를 어떻게 직렬화할지를 우리가 원하는 방식으로 덮어쓴다.
    - `GenericJackson2JsonRedisSerializer()`: Jackson을 이용해서 자바 객체를 JSON 문자열로 변환하는 직렬화기이다. `CouponResponse`(`record`)같은 객체를 저장할 수 있게 해주는 부분이다.

| 항목                   | JDK 직렬화 (바이너리)                                       | Jackson (JSON)                                 |
|------------------------|-------------------------------------------------------------|------------------------------------------------|
| 속도/CPU 비용          | 대체로 더 빠름 (변환 과정이 단순)                           | 상대적으로 느림 (텍스트 파싱/조립 필요)        |
| 저장 크기              | 클래스 메타데이터까지 포함돼서 의외로 큼                    | 보통 더 작거나 비슷함                          |
| 사람이 읽을 수 있나    | 못 읽음 (바이트 덩어리)                                     | 읽을 수 있음 (redis-cli로 봐도 알아볼 수 있음) |
| 다른 언어와 호환       | Java끼리만 가능 (Python, Node.js 등에서 못 읽음)            | 어느 언어에서든 JSON 파싱 가능                 |
| 클래스 구조 바뀌면     | 잘 깨짐 (serialVersionUID 불일치 등으로 역직렬화 실패 흔함) | 상대적으로 유연함 (필드 추가/삭제에 관대함)    |
| 보안                   | 역직렬화 취약점(RCE 등)으로 유명해서 실무에서 기피하는 추세 | 상대적으로 안전                                |
| Serializable 필요 여부 | 필수                                                        | 불필요                                         |

**3. 조회 메서드에 `@Cacheable(value = "coupon", key = "#couponId")`를 붙인다.**
- 처음에만 메서드 실행 결과를 캐시에 저장하고, 다음부터는 캐시 값만 바로 return 해준다.
  - 최초 호출
    - `couponRepository.findById()`를 조회하고, `coupon::{couponId}`로 Redis에 저장된다.
  - 이후 호출
    - `coupon(value)::{couponId(key)}`바로 반환한다. 
 
```redis
127.0.0.1:6379> GET coupon::1
"{\"id\":1,\"name\":\"쿠폰A\",\"totalQuantity\":100,\"issuedQuantity\":5}"
```

**4. 쿠폰 발급이 완료되면 `@CacheEvict(value = "coupon", key = "#couponId")`를 해준다.**
- 메서드가 정상적으로 끝났을 때, 지정한 캐시에서 해당 key의 데이터를 삭제한다.
- value = "coupon", key = "#couponId": getCoupon()의 @Cacheable과 정확히 같은 캐시 이름-키를 가리켜야 한다. 같은 대상을 가리켜야 "그 캐시를 지운다"는게 성립하기 때문이다.

이게 필요한 이유는 캐시데이터의 정합성 때문이다. `issue()`가 실행되면 실제 DB의 `issuedQuantity`가 바뀌는데, `@CacheEvict`가 없으면 캐시에는 발급 전의 옛날 값이 남아있게 된다. 그렇게 되면 이후 `GET /coupons/{id}`로 조회했을 때 실제와 다른 낡은 데이터를 응답하게 된다.

## [동작예시]
### 1. 첫 번째 조회 — `GET /coupons/1`

캐시에 coupon::1 있나? → 없음 (캐시 미스)<br>
→ getCoupon() 메서드 실제 실행<br>
→ DB에서 조회 (issuedQuantity: 0)<br>
→ 결과를 coupon::1 이라는 키로 Redis에 저장<br>
→ 클라이언트에 응답

### 2. 두 번째 조회 — `GET /coupons/1` (다시 호출)

캐시에 coupon::1 있나? → 있음 (캐시 히트)<br>
→ getCoupon() 메서드는 아예 실행 안 됨 (DB 조회 스킵)<br>
→ 캐시에 저장된 값을 그대로 반환

이 시점에는 몇 번을 조회해도 DB에 안 가고 계속 캐시에서만 응답한다.

### 3. 발급 — `POST /coupons/1/issue?userId=1`

issue() 메서드 실행<br>
→ DB의 issuedQuantity가 0 → 1로 실제 변경됨 (커밋됨)<br>
→ 메서드가 예외 없이 정상 종료됐으므로 @CacheEvict 발동<br>
→ coupon::1 캐시 삭제<br>

이 순간 캐시는 비어있는 상태가 된다. DB만 최신값(1)을 갖고 있다.

### 4. 세 번째 조회 — `GET /coupons/1`

캐시에 coupon::1 있나? → 없음 (3.에서 지워졌으니까, 다시 캐시 미스)<br>
→ getCoupon() 메서드 실제 실행<br>
→ DB에서 조회 (이번엔 issuedQuantity: 1, 최신값)<br>
→ 결과를 coupon::1로 다시 Redis에 저장<br>
→ 클라이언트에 응답

> 캐시 미스(DB 조회 + 캐시 저장) → 캐시 히트 반복 → 발급 발생(캐시 삭제) → 다시 캐시 미스(최신값으로 재저장) → 캐시 히트 반복 → ...

H2 Database로 TPS 테스트를 했을 때

| 지표         | 캐시 없음 (baseline) | 캐시 적용 후 |
|--------------|----------------------|--------------|
| avg          | 914.87µs             | 1.01ms       |
| p(95)        | 2.48ms               | 1.58ms       |     
| max          | 122.34ms             | 421.29ms     |
| iterations/s | 32,096.56            | 28,957.65    |
`avg`, `max`는 더 느려지고 악화되었다. `p95`는 개선되긴 했지만 가끔 느리게 나오는 상위 5% 케이스는 캐시가 있을 때 더 안정적으로 처리되었다. DB접근이 가끔 튀는 경우를 캐시가 완충해준 것이다.
- `avg`는 H2가 인메모리 형식의 DB라서 PK로 단일 행 조회하는 것은 매우 빠른 수준이다. 캐시를 붙이면서 오히려 "네트워크 왕복 + JSON 직렬화/역직렬화" 오버헤드가 추가되었기 때문이다.
- `max`는 HikariCP처럼 Lettuce의 커넥션 풀이 기본값으로 작게 잡혀있어서, VU 30개가 동시에 Redis에 접근하려다 병목현상이 생긴 것이다.

LettuceCP를 20으로 늘렸을 때 14% 정도 줄기는 했지만 캐시를 쓰는 순간, 매 요청마다 "Redis에 네트워크 왕복(로컬 소켓 통신) + JSON 역직렬화"라는 추가 단계가 항상 붙는다. 하지만 H2 직접 조회는 이 단계가 아예 없다. 그래서 아주 가끔 이 추가 단계에서 지연이 생기면, 원래 DB 직접 조회보다 더 튈 수 있는 여지가 구조적으로 존재한다. 풀 크기를 늘려도 "네트워크 홉이 하나 더 있다"는 사실 자체는 없앨 수 없다.

그래서 이번에는 MySQL로 진행을 해봤다.

| 지표         | 캐시 없음 | 캐시 적용 후 |
|--------------|-----------|--------------|
| avg          | 3ms       | 968.38µs     |
| p(95)        | 7.45ms    | 1.44ms       |
| iterations/s | 9,873.7   | 30,172.4     |
| max          | 161.32ms  | 362.71ms     |

`avg`, `p(95)`, `iterations/s` 세 지표 모두 확실한 개선을 보였고, `max`만 예외적으로 나빠졌다.(이건 앞서 얘기한 것처럼 Redis 네트워크 왕복 때문에 가끔 튀는 지연이 생기는 것 + 통계적으로 신뢰도 낮은 단일 최악값이라는 두 가지 이유가 같이 작용한 걸로 보인다)

로컬(localhost)이라 해도, TCP 소켓을 통한 통신은 완전히 공짜가 아니다. 
커널 레벨에서 패킷을 주고받는 오버헤드, OS 스케줄러가 프로세스를 바꿔치기하는 시간(context switching) 같은 게 매번 조금씩 들어간다. 
대부분은 이 비용이 무시할 만큼 작지만(수십~수백 마이크로초), 아주 가끔 OS가 다른 작업을 처리하느라 이 요청을 늦게 처리하는 순간이 생길 수 있다. 
이게 캐시 없을 때보다 "가끔 튀는 지연"이 생기는 구조적인 이유이다. 
캐시가 없으면 이 왕복 자체가 없으니 이런 지연도 없는 것이다.

결론: 나중에는 localhost가 아닌 서버에서 테스트를 해봐야겠다.
